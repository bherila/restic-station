# Contributing

Thanks for your interest in Restic Station. Two things make this repo unusual — read these before opening a PR.

**The Xcode project is generated.** `ResticStation.xcodeproj` is produced by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` — never edit the project file directly; edit `project.yml` and run `./scripts/bootstrap.sh`.

**`Core/` and `Helper/` are cross-platform; `App/` is macOS-only.** All logic lives in the `Core` Swift package; `Helper/` (the `restic-station-helper` executable, root SwiftPM package) depends only on `Core` + swift-argument-parser. Both must compile and pass their tests on **Linux** as well as macOS — that is the `linux` job in `.github/workflows/ci.yml` (`swift build && swift test` at the repo root, plus `swift test --package-path Core`, in a `swift:6.1` container), and it is a required check: a Linux-only compile error in `Core/` or `Helper/` fails it. Darwin-only API (`DistributedNotificationCenter`, AppKit, ServiceManagement, the Keychain `security` subprocess) belongs in `App/` or behind `#if os(macOS)` / `#if canImport(Darwin)`. Locally: `swift build`, `swift test --package-path Core` (works with a bare Homebrew Swift toolchain, no Xcode.app required — see `docs/testing.md`). Building/testing the Linux **static release** binary (Apple's Static Linux SDK, musl) is a separate, heavier path covered by `scripts/package-linux.sh` and the `release-linux`/`linux-integration`/`linux-runtime-verify` CI jobs — not needed for an ordinary `Core`/`Helper` change. Tests use Swift Testing (`import Testing`, `@Test`, `#expect`) — not XCTest.

**The spec docs in [`docs/`](docs/) are normative.** `architecture.md`, `data-model.md`, `restic-cli.md`, `scheduling.md`, `keychain-and-fda.md`, `ui-spec.md`, `testing.md`, `cli-json.md`, and `linux.md` define the intended behavior; the code implements them. If your change alters behavior, update the relevant doc in the same PR — a PR that makes code and docs disagree will be asked to reconcile them. State which platform(s) a change affects; most docs other than `ui-spec.md` (macOS-app-only) cover both. Key invariants to preserve (each has negative tests — keep them): all mutating restic operations go through `restic-station-helper`; keychain access only via the `/usr/bin/security` subprocess with `-T /usr/bin/security` at item creation (macOS); the Linux `secrets.json` is created `0600` and every read re-verifies that mode (fresh data directories are created `0700` without changing shared ancestor modes, existing ones are tightened before a secret is written, unprotected group/world write-and-search access on the directory or its immediate parent is refused, sticky ownership is honoured, and read/search exposure warns once without blocking the `0600` file; see `docs/linux.md` §Secrets and issue #49); never `forget` with an empty retention policy, never `forget`/`prune` a mirror that isn't caught up to the primary; `machine.json` is host-local and is never read or written by anything that touches `config.json`'s shared state.

CI must be green before merge: `linux` (Core + Helper on Linux), `macos` (app build, Core tests, real-restic integration script), `release-linux` (static Linux binary, both architectures), `linux-integration` (that binary's fixture-import flow against real restic on a bare Ubuntu VM), and `linux-runtime-verify` (the binary runs unmodified across several userlands with no Docker Desktop / colima needed locally — see `.github/workflows/ci.yml`).

**An independent review is anchored to an exact `(base SHA, head SHA)` pair.** Record both in the PR description, and re-state them after any rebase, force-push, or retarget: changing the base can change the diff even when the head commit is identical, so a review that passed against the old pair says nothing about the new one. **Before merge**, address findings as commits on the same branch rather than opening a parallel follow-up PR, and reply citing the fixing commit so the next reader does not re-derive the finding. If a finding arrives after merge, use a fix-forward PR and anchor its review to the new exact base/head pair. Note that GitHub marks a review thread "outdated" only when its anchor hunk changes — a finding fixed elsewhere in the tree stays non-outdated, and an unrelated edit can mark an unaddressed one outdated. Judge each thread against the code rather than against its badge.

**Destructive paths carry a higher bar.** Anything that can `forget`, `prune`, or `rewrite --forget` must state, in the PR, which invariant it touches and which way it fails if the new code is wrong. The standing invariants are in the paragraph above: never `forget` with an empty retention policy, and never `forget`/`prune` a mirror that isn't caught up to the primary. Prefer a change that fails closed and says why over one that fails open quietly — a destructive operation that refuses is recoverable, one that proceeds on stale evidence is not.
